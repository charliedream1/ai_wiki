# Self\-Harness：让 AI Agent自己改进自己的"操作框架"


自今年以来，Harness一直是热门话题，围绕其展开的新的研究方向也越来越多，上周上海人工智能实验室于2026\.6\.8日发布一篇论文《Self\-Harness: Harnesses That Improve Themselves》，对于这类前沿性的技术概念可以一起学习了解，论文中提到的 **Self\-Harness** 提出了一种Harness新范式：让 LLM Agent自己发现弱点、自己提出修改方案、自己验证效果——无需人类工程师或更强的外部模型参与，即可持续优化自身的运行框架（Harness）。

---

## 为什么需要 Self\-Harness？

### 1\.1 什么是 Harness？

通过前期的学习大家必然对Harness有了基本的理解：**模型本身 ≠ Agent**。一个Agent的表现由两部分共同决定：

同样的模型，换一个 Harness，表现可能天差地别。

### 1\.2 传统做法的瓶颈

论文指出当前，Harness 几乎全靠**人工设计**（如 ReAct、Claude Code、Codex、OpenHands 等）。这种"人肉调参"模式面临三个核心问题：

1. **模型特异性**：不同模型的"行为习惯"差异巨大——有的爱循环调用工具、有的经常忘生成产物文件、有的遇到错误就放弃。给 A 模型调好的 Harness，放在 B 模型上可能适得其反。

2. **模型迭代快**：LLM 几个月一换代，Harness 的适配跟不上。

3. **人力瓶颈**：每个模型都需要专门调优，工程师根本调不过来。

### 1\.3 已有方案的不足

- **自我改进类方法**（Reflexion、STOP 等）：调整的是记忆、上下文或响应策略，**不是** Harness 本身。

- **外部优化类方法**（Meta\-Harness）：用更强的模型来优化弱模型的 Harness——但强模型成本高，且对前沿模型来说根本不存在"更强的外部模型"。

---

## Self\-Harness 的核心思路

**核心洞察**：与其让人或更强的模型来调，不如让Agent**自己**来调——在当前 Harness 下运行 → 发现失败模式 → 提出修改 → 验证通过才采纳。

Self\-Harness 设计为一个**三阶段迭代循环**：


### 2\.1 阶段一：弱点挖掘（Weakness Mining）

**目标**：从执行轨迹中提取结构化的失败证据，而不是笼统的"这里做错了"。

具体流程：

1. 用当前 Harness 在 **held\-in** 数据集上跑一轮

2. 收集所有**失败**的执行轨迹

3. 对失败案例按 **验证器层面的失败签名** 聚类：

    - `c` = 终端验证器层面的原因（如"缺失必需产物"）

    - `q` = Agent行为与失败之间的因果关系（如"Agent未创建文件就宣告完成"）

    - `m` = 轨迹暴露的抽象机制问题（如"工具使用循环卡死"）

**关键设计**：输出的是**证据包（Evidence Bundle）**，只描述"什么失败了、为什么失败"，**不预设**该怎么改。这实现了诊断与处方的分离。

### 2\.2 阶段二：Harness 提案（Harness Proposal）

**目标**：基于失败证据，生成多样化的候选修改方案。

设计要点：

- **并行生成 K 个提案**，每个提案独立探索不同的修改方向

- **多样性**（跨提案）：不同失败机制 → 不同 Harness 修改面 → 不同假设

- **最小性**（提案内）：只改需要改的，不动无关部分，不做大范围重写

每个提案输出：一个有界的编辑 `Δ` \+ 审计记录 `a`

### 2\.3 阶段三：提案验证（Proposal Validation）

**目标**：只有真正有效的修改才能被采纳。

验证采用**保守的晋升准则**——候选 Harness 必须在 held\-in 和 held\-out （held\-in = 用来发现问题和提出修改的题，held\-out = 从不给模型看的题，只用来说明修改真的有效。）**两个**分割上都不退化，且至少在一个上有提升：

```Plain Text
Δ_held-in  ≥ 0  AND  Δ_held-out  ≥ 0  AND  max(Δ_held-in, Δ_held-out) > 0
```

**这意味着**：

- 只在训练集上刷分但泛化不好的修改 →  拒绝

- 训练集没变但泛化提升了 → 接受

- 两个都提升了 →  接受

多个兼容的候选编辑可以合并到下一个 Harness 版本中。

- 最大绝对提升 21\.4pp，最大相对提升 138%

### 3\.3 不同模型，不同"药方"

这是最有工程价值的发现——Self\-Harness 不是给所有模型加同一套"通用提示词"，而是针对每个模型的具体弱点对症下药：

## 案例深挖：看看 Harness 到底改了什么

### 案例一：MiniMax M2\.5 — 从"无限探索"到"聚焦执行"

**任务**：count\-dataset\-tokens（计算数据集 token 数）

**关键修改**：Bootstrap 指令改为"先识别所需输出产物并尽早创建初始版本"；运行时策略增加工具消息总数上限。

### 案例二：Qwen3\.5 — 从"删文件放弃"到"错误恢复"

**任务**：extract\-elf（提取 ELF 信息）

**关键修改**：添加了工具错误触发的恢复机制——当工具调用失败时，不是放弃，而是自动重定向到恢复流程。

### 案例三：GLM\-5 — 从"装完就忘"到"环境持久化"

**任务**：build\-pov\-ray（构建渲染器）

**关键修改**：Harness 指令确保环境变更跨 Shell 会话持久化，并鼓励从探索转向实施和测试。

## 我们从论文中学到什么：Self\-Harness 的核心设计原则

从这篇论文中，我们可以提炼出几个可直接迁移到工程实践的设计原则：

### 原则一：Harness 改进 = 经验性的状态迁移

一个有效的 Harness 编辑必须明确声明：

1. **目标行为**：它想改变什么行为

2. **修改面**：它改了 Harness 的哪个部分

3. **证据**：什么失败证据促成了这个修改

4. **评估结果**：什么测试结果证明了这个修改值得采纳

### 原则二：诊断与处方分离

弱点挖掘阶段只输出"什么失败了"，不输出"该怎么改"。这避免了过早收敛到局部最优解。

### 原则三：多提案并行 \+ 最小化修改

- 多提案并行探索，避免"只想到一种改法"

- 每个提案内部保持最小化修改，避免"牵一发动全身"

### 原则四：回归测试 \+ 双分割守卫

- 任何修改必须在训练集和验证集上都不退化

- 防止过拟合训练集的"刷分"式修改

- 可类比于软件工程中的 CI/CD 流水线

### 原则五：Harness ≠ Prompt Engineering

Harness 是一个比 Prompt 更大的概念——它包括提示词，但也包括工具定义、运行时机制、验证规则、编排逻辑、故障恢复流程等。很多时候**Agent的失败不是模型的问题，而是 Harness 的问题**：

- 不检查产物就报告成功 → 缺少验证机制

- 反复重试无效操作 → 缺少循环打断机制

- 环境变更丢失 → 缺少持久化机制

- 遇错即放弃 → 缺少恢复流程

---

## 局限性与未来方向

**论文指出的未来方向**：走向一种"记录化、可测试、可回滚"的 Harness 工程风格——自我改进应建立在**行为证据**之上，而不仅仅是提出者对"合理性"的论证。

---

## Takeaway

> **Self\-Harness 的核心启示：Harness 改进应该被视为一种经验性的状态迁移。**
> 
> 

对于做 Agent 工程的同学，这篇论文至少带来三个实操启发：

1. **别只盯着模型**——当 Agent 表现不佳时，先看 Harness 是否给模型提供了正确的行为约束和恢复机制

2. **让数据说话**——用执行轨迹做证据驱动式的 Harness 迭代，而不是拍脑袋调 Prompt

3. **测试守底线**——任何 Harness 变更都要有回归测试保护，防止"修了一个 bug 引入三个 bug"
